# ADR 006 — Explicit native device enrollment and legacy activation

Status: implemented in the development branch; desktop acceptance, independent protocol review and production API 2 rollout remain gates.

An owner root may authorize independent devices for its stable user. Partner invitation remains a separate API 1 workflow. This stage uses user-selected signed JSON files and native panels for enrollment; it adds neither a second invitation server nor a shared user private key.

The existing root exports a 30-minute signed offer containing its public authorization archive and C1 binding. This local enrollment lifetime is independent from the partner invite's current 10 minutes/formal 8 hours and from 60-second challenges/tickets. A fresh device validates the offer after the user compares its 96-bit code, generates an independent Ed25519 key in a staged replica directory, and exports a proof-of-possession request. The root compares the request's code and fingerprint, signs its existing owner authorization stream, and exports a completion bound to that exact request, genesis and origin. Per-offer durable claims prevent substituting a different request. Retries do not mint another grant; completed exports include current known authorization, including later revocations.

The new device verifies the completion and its own staged key before preparing an empty store. Only then does an exclusive `active-replica.json` select `Replicas/<offer UUID>`. The old unpaired bootstrap store remains intact. Devices with existing business data/pairing are refused; this is not an automatic account merge. Established missing keys stop recovery instead of rotating identity. The new replica fetches and verifies full history through the existing C1 engine; activating a file does not mean history is already synchronized.

For the two original Macs, first complete their normal old-protocol sync. Export one migration proposal, compare the same code on both machines, import/countersign it locally, return the co-signed file and explicitly activate on each Mac. Both pinned original roots must sign the exact current legacy inventory. Checks before and after the service request and during activation reject concurrent legacy changes. User IDs, keys, SharedSpace, original SignedOperation bytes, old peer and V1 binding are preserved. After V4 writes, an old binary is not a safe rollback reader; no data reset is a rollback strategy.

Only the original owner root can grant/revoke its devices in this version. Losing that root key cannot be repaired from relay/public logs, a role label or the partner's approval. Existing authorized replicas retain their valid local history, but root-only control requires the original private key. Exact original-identity backup restoration, root rotation and recovery UI need a separately reviewed design; a new device must never receive another device's private key. Unknown revocations while offline remain a freshness limitation; current exports must include all revocations already known to the issuer.

QA uses an independent app/Runner bundle, private temporary roots, file-only fixture keys and an explicitly configured loopback origin. It cannot fall back to production startup or a signed imported production endpoint. Synthetic partner automation is a local integration fixture, not evidence of two physical Macs or independent users completing the workflow.
