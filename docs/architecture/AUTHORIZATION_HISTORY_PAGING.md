# Authorization history paging assessment

Current status: **NOT IMPLEMENTED**; current metadata bound fails closed. No production Durable Object migration or protocol change is performed here.

Relay API 2 stores the complete signed authorization archive beside V1 routing state. The client verifies both owner chains, preserves historic public keys, and uses the archive digest during handshake. Server requests/storage are capped at 131,072 encoded bytes. The checked-in synthetic enrollment vector contains a 1,398-byte genesis and a 778-byte grant; that size is an illustration, not a fixed grant-size guarantee. A long history of grant/revoke cycles eventually reaches the cap even though active devices are limited to 32. Raising the cap or deleting revoked history does not establish safe scalability.

A compatible next step requires a negotiated authorization-inventory capability, with an immutable genesis and per-owner head digest/revision. Each bounded page must be pinned to those heads and a pass identifier, contain contiguous signed events, and supply a cursor that cannot switch owners/heads halfway through. Verify and stage all required pages before atomically promoting current trust. Retain prior trust on interruption; unknown grants must not authorize operation payloads. New clients must still understand complete API 2 archives; old clients need an explicit capability/size failure rather than partial silently trusted history.

This is separate from operation-inventory paging: public device-control history is the prerequisite for verifying operation epochs and revoked prefixes. Implementation spans Worker endpoints and additive DO records, client persistence/staging, handshake capability negotiation, enrollment archive references, portable schemas/vectors and failure-recovery tests. It needs dedicated compatibility tests for V1 routes, existing V2 archives, concurrent owner updates, equivocation, missing pages, rollback/replay, revocation during transfer and resumption after process death. Storage and cold-start/verification measurements must use long revoke/grant histories.

Keep the old full archive until a new root/head-pinned representation is verified and clients negotiate it. A rollout should first add read-compatible endpoints/records, then opt-in clients, with a rollback that does not discard signed events or downgrade already-known trust. No reliable calendar estimate is justified before that separate prototype and cost measurement. It is a release/longevity limitation, not a reason to reset spaces or keys in this task.
